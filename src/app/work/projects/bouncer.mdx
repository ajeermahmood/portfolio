## What it is, in one minute

More people can write code now than a year ago. A designer can ship a page, a support lead can fix their own copy, and an AI agent can open twenty pull requests before lunch. Code review did not get faster to match. So the hard part moved: it is no longer writing the change, it is knowing the change is safe.

`bouncer` is a small tool that stands at the door of your main branch and checks every change for a short list of mistakes that are expensive when they reach production. If it finds one, it tells you the file, the line, and what to do instead. You do not need to already know that the `orders` table is tenant-scoped, or that you cannot store money in a float. The tool knows, and it tells you.

Try it in ten seconds:

```
npx bouncer-gates
```

Or paste some code into the [playground](https://bouncer.ajeermdk001.workers.dev) and watch it run. It is MIT licensed and on npm as [`bouncer-gates`](https://www.npmjs.com/package/bouncer-gates). The rules come from running these same checks across eight production codebases, mostly a multi-tenant e-commerce platform. The longer story of why checks beat instructions is in [Making a codebase safe for AI coding agents](/blog/coding-agents-in-production-repositories).

## The five things it checks

Each check is called a gate. A gate either lets a change through or stops it with a reason.

1. **Secrets.** An API key, a password or a private key pasted into the code. It also reads committed `.env` files, and knows the difference between a real key and a placeholder like `${DB_PASSWORD}`.
2. **Tenant scope.** In an app where many customers share one database, a query that forgets to filter by customer shows one customer another customer's data. This gate catches list-style queries on tenant-owned tables that never mention the tenant column.
3. **Money.** `Math.round(price * 100)` and `parseFloat(amount)` are the two classic ways to lose cents. Floats cannot hold money exactly.
4. **Migration safety.** A new database migration that adds a `NOT NULL` column with no default, or renames a column, breaks the version of the app that is still running while the deploy happens.
5. **Doc links.** A link in a README that points at a file someone deleted last month.

That is the whole list on purpose. Anything a formatter, a linter or a compiler can already check does not belong here.

## Where it runs

The same five gates run in four places, and it is the same code in all four:

- **In CI.** A GitHub Action, `uses: ajeermahmood/bouncer@v0`, blocks the merge and can post findings to the GitHub Security tab.
- **In your editor, next to the AI agent.** This is the newest part. CI sees a mistake after the pull request exists. An agentic editor like Claude Code or Cursor can see it in the same turn the mistake was made. `npx bouncer-gates --init-agents` wires the gates in as an MCP server and a post-edit hook, so the agent gets told "this query is not tenant scoped" the moment it writes the line, not twenty minutes later in a red CI check.
- **In a Cloudflare Worker and on Railway.** The playground on the site sends your snippet to the worker, and a hosted API on Railway serves teams that want the checks over HTTP without running Node.
- **In the browser.** If the worker is unreachable, the playground runs the same gate code locally and the footer says so.

Each gate is a plain function: files in, findings out. No filesystem, no git, no environment variables, no printing. All of that lives in one runner. That one decision is why the same code can run everywhere without four copies of the rules drifting apart.

## Getting started on an existing codebase

Two commands:

```
npx bouncer-gates --init          # writes a starter bouncer.config.json
npx bouncer-gates --init-agents   # wires the gates into Claude Code and Cursor
```

If the repository has a Prisma schema, `--init` reads it, finds every model with a `tenantId` field, and fills in the tenant scope config for you. It guesses the tenant column from whatever owner-shaped field appears on the most models, so a schema built on `storeId` works too. The doc-links repo URL comes from your git remote.

An old codebase will already have things wrong in it. Nobody fixes two hundred findings before merging anything else, so `--baseline-write` records what is already there. Old findings stop blocking, new ones block right away, and the debt stays visible and countable.

If a gate is wrong about one specific line, you tell it so on the line:

```js
// bouncer-ok(scope): finance dashboard, spans all tenants by design
```

The reason is required. A bare marker suppresses nothing. That way the excuse lives in the file where the next reader will find it, not in a pull request nobody will open again. There is deliberately no switch to turn a gate off across the whole repository. If a gate is wrong that often, the gate is what needs fixing.

## The number that mattered was the false positives

Anyone can write a checker that catches the bad case. The hard part is not crying wolf.

I pointed an early build at a real 1,209 file production monorepo. It reported 45 blocking findings. I read all 45 by hand, and 32 were wrong. A tool that is wrong a third of the time gets switched off within a month, and then it protects nothing while still sitting in the workflow file making everyone feel covered.

The false positives came in three families:

- **Test fixtures.** Fake credentials inside `.spec.ts` files were a third of all findings, and every one was on purpose. They now report as warnings, not blocks. One exception stays blocking: an `sk_live_` Stripe key in a test file is not plausible fake data.
- **Percentages.** `Math.round(x * 100)` is both the classic money bug and the normal way to render a percentage. The tell is a division inside the rounded expression. A percentage is a part over a whole. Money conversion never divides before it scales.
- **Local dev credentials.** `postgres:postgres@localhost` in a setup script's help text grants nothing to anyone.

After fixing those, the same repository reports 13 findings and all 13 are real. Every one of the 32 false positives is now a test that asserts the gate stays quiet, named for what the mistake actually was. The suite is at 115 tests, and the most valuable ones are the ones that document a mistake the tool really made.

## One rule everything else serves: never fail open

"We looked and it was fine" and "we could not look" are different answers, and only one of them is safe to merge on.

The migration gate compares against the base branch to find new `.sql` files. On a shallow CI clone there is no base branch, so nothing looked new, so the gate printed a reassuring "no new migrations" and would have printed it forever. Now the skip reason is a sentence, not a boolean, so those two cases cannot look the same:

```
skip  migration-safety (cannot see history: the base ref "origin/main" is not in
      this clone, so no migration can be identified as new)
```

The same rule runs through everything. A gate that throws is a failure, not a silence. A typo in a command-line flag exits with an error instead of being ignored and quietly scanning nothing. Inside the editor, a gate that could not run is listed next to the findings, because an agent told "the code is clean" when the scope gate never ran would learn the wrong thing.

## It got four times faster, and none of it was clever

Total scan time on that same repository went from 291ms to 73.6ms. Three fixes did almost all of it, and none of them were visible until measured: a regex was being compiled once per line per gate, roughly a million times. The scope gate rebuilt a matcher inside its inner loop. And each gate now tests one combined pattern against the whole file before looking at any line, because almost every line contains nothing interesting.

Worker threads were considered and rejected. At 73ms, starting a thread pool costs more than the work.

## What it deliberately does not do

It is not a replacement for gitleaks or trufflehog, which scan git history for secrets far more thoroughly. It is not Semgrep, which is a real static analysis engine. It is not ESLint, which owns everything about the shape of the code.

Every gate documents what it misses, and those lists are the specification. The scope gate cannot follow a client passed into a transaction callback, which is the single most likely place a real cross-tenant leak survives a green build. It cannot know whether a written excuse is still true a year later. A tool that claims to catch everything teaches people to stop reading, and then the one it missed ships.

## Anonymous telemetry, and how to turn it off

One ping a day: a random id, the version, the runtime, the OS and the Node major. Nothing about your code. `BOUNCER_TELEMETRY=0` or `DO_NOT_TRACK=1` switches it off, the first run says so, and the [full list of what it sends](https://github.com/ajeermahmood/bouncer/blob/main/docs/telemetry.md) is in the repository.
